# Plan prompts

> Two prompts live here: **1. Create the plan** (run it to generate `doc-ai/core/plan/plan.md`) and **2. Execute a phase** (the generic prompt for every execution session).

## Prompt 1 — Create the plan

Create REPMA's phased plan. First READ — not skim, and never cite a doc you haven't opened:

- `doc-ai/core/`: spec.md, architecture.md, database.md — the source of truth; the plan does not reopen any decision already made (AD/DP/RN/RF by ID, never copy their content).
- `doc-ai/design/`: DESIGN.md, shared/ (layout.md, components.md, product-picker.md) and **every page doc in pages/ that the plan will schedule**. A plan sub-task must never contradict a page doc (which page owns which component/flow, what each page's add-surface is); if a scheduled page's doc is marked pending, the sub-task that builds the page starts by writing that doc.
- `doc-ai/features/README.md` and the spec of any feature the plan schedules as an optional phase.

Plan rules:

1. Each phase is a self-contained increment: it ends DEPLOYED, TESTED and COMMITTED. If I abandon the project at the end of any phase, what's on main is a presentable, coherent product — never a skeleton or something half-done.
2. VERTICAL slices (one complete feature DB→API→UI), never horizontal ("all the backend first" is forbidden).
3. Phase 1 = foundations: monorepo, migrations, RLS with its isolation tests (the hardest part goes first), auth, green CI and a working deploy even if it only serves the health check. Deploy is never left for the end.
4. Scope: MVP only, per the spec. Features 003–005 (doc-ai/features/) go as optional phases at the end, clearly marked as non-MVP; the E2E smoke (PD-02) as an optional phase before them.
5. Session decisions (AD-23/RF-43) and the landing decision (DP-01: in the final polish phase, `/` redirects to /login) are already closed in the docs — the plan respects them, it doesn't reopen them.
6. No over-engineering (CLAUDE.md): each phase justifies its complexity with an existing requirement.
7. MY MANUAL TASKS: anything the agent can't do that I have to set up by hand (creating the Supabase project, copying its keys, setting up Render, GitHub Actions secrets, Storage buckets…) goes in a separate "Manual setup" section of the phase that needs it. Every credential/config ends up in environment variables — never hardcoded — but **distinguish where each one lives**: the API's runtime environment (local `.env` with its versioned `.env.example`, and the deploy service) carries ONLY what the running API needs; CI-only secrets (the admin/migrations connection string, deploy hooks) live in GitHub Actions secrets and are validated by the scripts that use them, NEVER by the API's env validation and NEVER set on the deploy service — the admin DB credential must be impossible to find inside the runtime container. Each manual task is explained step by step as if I knew nothing (where to click, what to copy, where to paste it) and ALWAYS ends with its verification: a concrete command or check that tells me whether I did it right and what error to expect if I didn't.
8. MANUAL TASKS ARE EXECUTABLE AT THEIR POINT IN TIME: every tool a manual task's steps or verification uses is installed by an earlier step (if a verify runs `psql`, something before it installs `psql`); every artifact a manual task references (`.env.example`, a DB role and its password, a bucket, a secret) has a named owner — the sub-task that creates it — scheduled BEFORE the manual task needs it; if a value genuinely can't exist yet (created in a later sub-task), the task must say so explicitly and get a second verification step after that sub-task, never a verify that silently tests only half the task. Connection values must be written exactly as the provider requires them (e.g. pooler usernames), and every credential's provisioning mechanics (how a password is set without ending up in a versioned file) must be spelled out, not assumed.
9. SHORT SESSIONS: I work in ~1-2h sessions. Each phase is broken into sub-tasks of that size, each closable green on its own (tests passing + commit): the real save point is the session, not the phase. Each phase also starts with a "starting state" — what already exists and what command verifies it's still green — so a new session can orient itself in two minutes without rereading everything.
10. FULL TRACEABILITY: every RF, RN, RNF, DP and AD in the core docs must be assigned to a concrete sub-task (or explicitly listed as out of the MVP with the reason). Never cite an ID range (`RNF-01..09`) as coverage: expand it and place each member — ranges are how requirements get silently dropped. A citation must match the ID's actual content (don't hang an obligation on an ID that says something else).

Format: for each phase — one-sentence objective, scope (RF/AD it covers), verifiable deliverable ("what I can show once it's done"), tests that must pass, and closing criterion. Numbered, with a relative size estimate (S/M/L). The plan is saved in `doc-ai/core/plan/plan.md` and also serves as the progress tracker: phases and sub-tasks are checked off as they're completed.

SELF-VERIFICATION before presenting: once the draft is written, audit it against the docs — do not skip this or hand it to me unaudited. Check at minimum: (a) every cited ID exists in its doc and means what the plan uses it for; (b) every ID in the core docs is covered per rule 10 — list the uncovered ones and resolve them; (c) every design page doc the plan schedules was actually read and no sub-task contradicts it (component ownership, page flows, shared primitives and who introduces them); (d) no sub-task or manual task consumes something (role, file, bucket, variable, component) created later — walk the timeline; (e) every manual task passes rule 8 (tools installed, owners exist, verification runs at that point); (f) the endpoint and route surface in architecture.md is fully placed. Fix what the audit finds, then present the plan.

Known traps — concrete findings from the review that discarded the previous plan. The rules above cover the general classes; these are the specific mistakes it made. Do not repeat them:

- **Picker ownership inverted:** the ProductPicker's "Add to assortment" flow belongs to `/availability` (its header action); `/catalog` never opens the picker — its only add surface is its slide-over. Source: `product-picker.md` §Consumers, `catalog.md`. The previous plan built the picker into `/catalog` and forgot the slide-over entirely.
- **`<SizeRun>` is the shared primitive and the picker consumes it** — not the other way around. `<SizeRun>`, `<ProgressBar>`, `<RequirePermission>`, the filter band (URL-held state, debounce) and the dialog portal (mandatory before the first modal ships) all need an owning sub-task; the previous plan never scheduled any of them.
- **Nobody owned the design-token layer:** DESIGN.md's Tailwind theme from CSS custom properties, `layers` z-index scale, self-hosted fonts and the Material Symbols subset are needed by the very first page (`/login`) — give them an explicit home.
- **Headless UI vanished:** RNF-19 mandates Tailwind + Headless UI as the single styling stack; put it in the stack from the first UI sub-task instead of hand-building Dialog/Listbox/Menu.
- **RNF-08 / AD-13 went unowned:** Zod request validation (whitelisting body/query/params, per-field issues, schemas shared api↔web) on ALL endpoints needs its own line in the Phase-1 API skeleton — env validation alone is not it.
- **Rate-limit families:** architecture §3.3 mounts a limiter in every router; make "mount the right family" part of each API sub-task's done, so the final audit verifies instead of remediating.
- **Isolation suite was too narrow.** Beyond per-tenant-table cross-tenant read/write, it must cover: `tenants` SELECT by a store user (global table — a per-tenant-table sweep misses it); `availability_events` WITH CHECK `created_by = uid()` (same-tenant event attributed to another user must fail); platform_admin with role set but no `app.tenant_id` → 0 rows on tenant-scoped tables; non-admin writes to global tables blocked at the *policy* layer (not only per-route authz); deny-by-default enumerated over all 9 tables, not just the 4 tenant-scoped ones. Ledger-immutability asserts "fails", not "fails with an RLS error" (it's enforced by grants too).
- **Seed vs Storage timing:** the product-images bucket doesn't exist until its phase creates it — the Phase-1 seed uses NULL/placeholder image URLs (or bucket creation moves earlier). And keep database.md §9's demo-critical details: out-of-stock sizes populated from first startup, an empty draft list, overlapping + exclusive assortments across the two stores.
- **`repma_api` mechanics:** specify how its password is provisioned (never in a versioned migration — e.g. a non-versioned bootstrap step or dashboard SQL); give `DATABASE_URL` its own verify once the role exists (`psql "$DATABASE_URL" -c 'select 1'` + a no-context select returns 0 rows); Supabase session-pooler usernames are tenant-qualified (`postgres.<project-ref>`, `repma_api.<project-ref>`); `psql` must be installed by a prerequisite step; `.env.example` needs an owning sub-task before any manual task reads it.
- **Admin/migrations URL leaked into runtime:** it is a CI-only secret (rule 7) — never in Render's env nor in the API's env schema.
- **Endpoint lists written exactly:** `GET /users/:id` exists in architecture §7 and got lost in shorthand; enumerate `/:id` routes explicitly. Register `GET /availability/events` before `/availability/:id` where the router is born (with the order asserted), not as a later-phase retrofit.
- **The landing page doc is pending** in `pages/README.md` — its sub-task starts by writing it (per the reading-list rule).
- **Size honestly:** the previous auth sub-task bundled the permission matrix + authenticate middleware + three endpoints + tests in one "session"; split anything that can't plausibly close green in ~2h.

Don't implement anything yet: just the plan, and present it to me for review before saving it.

Last task of this same session, once the plan is approved: review the "Prompt 2 — Execute a phase" section below (it already exists) and update it only if the approved plan changed something it relies on (doc locations, the starting-state ritual, the green criterion); otherwise leave it untouched.

## Prompt 2 — Execute a phase

Work session on REPMA. **Execute Phase X of the build plan at `doc-ai/core/plan/plan.md`** (I set the phase number by hand each session — if it doesn't match the plan's first phase with unchecked sub-tasks, stop and tell me before doing anything). Documentation: `CLAUDE.md` is the entry point (working rules + doc map — follow both); the session diary is `doc-ai/core/plan/journal.md`.

1. **Orient (max ~5 min):** read `plan.md` and locate Phase X's next unchecked sub-task. Read the latest `journal.md` entry for anything left pending. Read only the docs the sub-task's scope IDs point to (per CLAUDE.md's doc map) — nothing else.
2. **Verify the starting state before touching anything:** run the phase's "starting state" verification (and `npm run check` once it exists). If it's not green, fixing that IS the session's first job — nothing new gets built on red. If a manual-setup task I haven't done blocks the sub-task, stop and tell me exactly which one, with its verification.
3. **Execute ONLY sub-tasks of Phase X, in order, one at a time.** Each sub-task closes green on its own: its tests pass, `npm run check` passes, then commit (this is the standing authorization to commit — one commit per closed sub-task, never mid-task). If the session ends mid-sub-task, do not commit half-work: leave it in the working tree and record the exact stopping point in the journal. Never start a sub-task that can't plausibly close within the session.
4. **Respect the docs:** the core docs are the source of truth — reference AD/RF/RN/DP by ID, reopen nothing. If executing reveals a genuine gap or forces a decision, record it in the right core doc (new/updated ID) and mention it in the journal — decisions never live in `plan.md` or `journal.md`.
5. **Close the session:** append an entry to `journal.md` using its template (done / deviations / pending), check off completed sub-tasks (and the phase + its closing criterion, if reached) in `plan.md`, and finish with a short summary: what closed, what's next, and any manual task waiting on me.
