# Global catalog — `/platform/catalog`

> Guard: `catalog:manage` · Zone: platform
> API: `GET/POST /categories`, `PATCH /categories/:id`, `GET/POST /products`, `PATCH /products/:id`, `POST /products/:id/sizes`, `PATCH /products/:id/sizes/:sizeId`, `POST /products/:id/image`

## Purpose
Platform Admin management of the global catalog: categories, products and their sizes (RF-13..17, RN-02). Every product has ≥1 size — label, per-size unique SKU, position, `is_active`; non-sized products carry a single size labeled "One size". Distinct from the read-only store view at `/catalog`. Platform-zone page: no `X-Tenant-Id` on any call (architecture.md §5.2 — the catalog router is global).

## Layout
Shell per ../shared/layout.md. Below the `<PageHeader>` ("Global catalog"), **two tabs**: "Categories" and "Products". Active tab lives in the URL (`?tab=categories|products`, default `products`) — shareable and refresh-safe, consistent with the filter-state convention in ../shared/components.md. Each tab renders the standard list skeleton (filter band → `<DataTable>` → `<Pagination>` where paginated). The primary action button in the header follows the active tab ("New category" / "New product").

## Content

### Tab "Categories"
Table (from `GET /categories`; not paginated — small closed set):
| Column | Source | Notes |
|---|---|---|
| Name | `name` | body-medium |
| Slug | `slug` | muted |
| Description | `description` | truncated with ellipsis; "—" when empty |
| Products | product count | **Nice-to-have**: only if the API includes a count; omit the column otherwise |

Row action: "Edit". **No delete button** — a category with products cannot be deleted (RF-14, FK RESTRICT) and category deletion is not in the API surface for the MVP.

Create/edit modal: **Name** (required), **Description** (optional). Slug generated by the API (RN-10), shown read-only in the edit modal.

### Tab "Products"
Table (from `GET /products`, paginated):
| Column | Source | Notes |
|---|---|---|
| (thumb) | `image_url` | 32px thumbnail; neutral placeholder when null |
| Name | `name` | body-medium |
| Sizes | size count | muted, tabular (e.g. "6 sizes", "1 size"); SKU lives per size, so there is no SKU column |
| Category | category name | |
| Status | `is_active` | "Active" / `badge-inactive` "Inactive" (one status label everywhere — `../shared/components.md` §Data conventions; "Retire" is the action verb, never the label) |

Filters (URL state): search ("Search by name or SKU…" — matches product name or any size SKU) + category select ("All categories") + status select (All / Active / Inactive) → `search`, `categoryId`, `isActive` (RF-15).

Row actions: "Edit", "Retire" (active products) / "Reactivate" (retired ones). No hard delete (RN-08).

**Create modal**: product fields — **Name**, **Category** (select from `GET /categories`), **Description** (optional), **Image** (file input, jpg/png, ≤5MB) — plus a **sizes editor**:
- Preset buttons "Clothing" (XS/S/M/L/XL/2XL), "Footwear" (36–45), "One size" prefill editable rows from the shared size-preset constants; labels stay freely editable per product.
- Each row: **Size** (label) + **SKU** (unique per size). Rows can be added and removed freely before creation.
- ≥1 size required — enforced by the shared Zod schema (and by the API on `POST /products`).

**Edit modal**: the same product fields, with sizes managed in an expandable "Sizes" section of the same modal:
- Existing sizes: edit label, SKU (global uniqueness enforced — 409 handled as in create) and position, toggle active/inactive (soft — same confirm pattern as product retire/reactivate) → `PATCH /products/:id/sizes/:sizeId`.
- Add new sizes → `POST /products/:id/sizes`.
- **No delete** of existing sizes — deactivation only (referenced sizes are protected regardless).

The image stays per product (one image, not per size).

## States
Defaults from ../shared/components.md apply. Page-specific:
- Products empty state: "No products yet" + "New product"; with filters: "No results" + "Clear filters".
- Retired products stay listed (default status filter: All) with `badge-inactive` "Inactive"; they remain editable.
- Image upload pending: modal shows a per-field uploading indicator; the submit flow stays disabled until it resolves.

## Flows

### Create product (create-then-upload)
1. "New product" → modal. Fill product fields, then build the size rows (preset button prefill or manual rows). Submit → `POST /products { name, categoryId, description?, sizes: [{ label, sku, position }] }` (**no image in this call**; ≥1 size required, Zod + API).
2. On success, if an image was selected: `POST /products/:id/image` (multipart) with the returned id — the product stores the URL (RF-17).
3. Both OK: close, toast "Product created", invalidate products list.
4. Product created but image upload failed: close is still valid — toast error "The product was created, but the image upload failed. Try again from Edit." Invalidate list; never retry `POST /products`.
5. **409 (duplicate SKU)**: inline error on the offending size row "A size with this SKU already exists"; modal stays open. 400: inline field errors (missing sizes: "Add at least one size").

### Edit product
1. "Edit" → prefilled modal. Submit → `PATCH /products/:id` (changed product fields only); if a new image was chosen → `POST /products/:id/image` after the PATCH succeeds.
2. Success: close, toast "Product updated", invalidate list.
3. Size edits in the "Sizes" section are their own mutations: label/SKU/position change → `PATCH /products/:id/sizes/:sizeId`; new row → `POST /products/:id/sizes`. 409 on a size SKU (create or edit): inline error on that row.

### Deactivate / reactivate size
1. Toggle on an existing size → confirm modal (same pattern as product retire): "Deactivate size “42” of “Nike Air Max”? It can no longer be added to assortments or lists; existing entries and history are unaffected." Confirm is `button-danger`; reactivation uses `button-primary`.
2. Confirm → `PATCH /products/:id/sizes/:sizeId { is_active: false|true }` (soft — sizes are never deleted).
3. Success: toast "Size deactivated" / "Size reactivated", invalidate the products list (size counts) and the open modal's data.

### Retire / reactivate product
1. "Retire" → confirm modal (RN-08 copy states the effect): "Retire the product “Nike Air Max”? It can no longer be added to assortments; existing entries and history are unaffected." Confirm is `button-danger`. Reactivation: "Reactivate…?" with `button-primary`.
2. Confirm → `PATCH /products/:id { is_active: false|true }` (soft, RF-16).
3. Success: toast "Product retired" / "Product reactivated", invalidate products list (and any assortment-picker queries elsewhere).

### Create / edit category
1. Modal submit → `POST /categories { name, description? }` / `PATCH /categories/:id`.
2. Success: close, toast "Category created/updated", invalidate categories list **and** the category filter/select options.
3. 409 (slug conflict, RN-10): inline error on Name "A category with an equivalent name already exists".

## Edge cases
- Image > 5MB or wrong type: reject client-side before upload (inline error "The image cannot exceed 5 MB"); still handle the API 413/400 with the same inline error.
- Preset buttons ("Clothing", "Footwear", "One size") replace the current size rows in the create modal; if rows already have content, confirm before overwriting. Presets are prefill only — the shared constants never constrain what labels a product may use.
- Category select in the product modal has no "create category" shortcut — switch to the Categories tab (keep MVP simple).
- Switching tabs preserves each tab's own filter params in the URL or resets them — pick one; resetting the other tab's params on switch is the simpler contract. Tab switch never loses in-progress modal state (modals block navigation naturally).
- A retired product referenced by existing assortments/lists renders normally in store views (RN-08); nothing to handle here beyond the confirm copy.
- Editing a product's category is allowed (FK RESTRICT only guards category deletion, which the MVP doesn't expose).
