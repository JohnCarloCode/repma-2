# Global catalog — `/platform/catalog`

> Guard: `catalog:manage` · Zone: platform
> API: `GET/POST /categories`, `PATCH /categories/:id`, `GET/POST /products`, `PATCH /products/:id`, `POST /products/:id/sizes`, `PATCH /products/:id/sizes/:sizeId`, `POST /products/:id/image`

## Purpose
Platform Admin management of the global catalog: categories, products and their sizes (RF-13..17, RN-02). Every product has ≥1 size — label, per-size unique SKU, position, `is_active`; non-sized products carry a single size labeled "One size". Distinct from the read-only store view at `/catalog`. Platform-zone page: no `X-Tenant-Id` on any call (architecture.md §5.2 — the catalog router is global).

## Layout
Shell per ../shared/layout.md. Below the `<PageHeader>` ("Global catalog"), **two tabs**: "Categories" and "Products". Active tab lives in the URL (`?tab=categories|products`, default `products`) — shareable and refresh-safe, consistent with the filter-state convention in ../shared/components.md. Each tab renders the standard list skeleton (filter band → `<DataTable>` → `<Pagination>` where paginated). The primary action button in the header follows the active tab ("New category" / "New product").

## Content

### Tab "Categories"
Table (from `GET /categories`; not paginated — small closed set):
| Column | Source | Notes |
|---|---|---|
| Name | `name` | body-medium |
| Slug | `slug` | muted |
| Description | `description` | truncated with ellipsis; "—" when empty |
| Products | product count | **Nice-to-have**: only if the API includes a count; omit the column otherwise |

Row action: "Edit". **No delete button** — a category with products cannot be deleted (RF-14, FK RESTRICT) and category deletion is not in the API surface for the MVP.

Create/edit modal: **Name** (required), **Description** (optional). Slug generated by the API (RN-10), shown read-only in the edit modal.

### Tab "Products"
Table (from `GET /products`, paginated):
| Column | Source | Notes |
|---|---|---|
| (thumb) | `image_url` | 32px thumbnail; neutral placeholder when null |
| Name | `name` | body-medium |
| Sizes | size count | muted, tabular (e.g. "6 sizes", "1 size"); SKU lives per size, so there is no SKU column |
| Category | category name | |
| Status | `is_active` | "Active" / `badge-inactive` "Inactive" (one status label everywhere — `../shared/components.md` §Data conventions; "Retire" is the action verb, never the label) |

Filters (URL state): search ("Search by name or SKU…" — matches product name or any size SKU) + category select ("All categories") + status select (All / Active / Inactive) → `search`, `categoryId`, `isActive` (RF-15).

Row actions: "Edit", "Retire" (active products) / "Reactivate" (retired ones). No hard delete (RN-08).

**Create modal**: product fields — **Name**, **Category** (select from `GET /categories`), **Description** (optional), **Image** (file input, jpg/png, ≤5MB) — plus a **sizes editor**:
- Preset buttons "Clothing" (XS/S/M/L/XL/2XL), "Footwear" (36–45), "One size" prefill editable rows from the shared size-preset constants; labels stay freely editable per product.
- Each row: **Size** (label) + **SKU** (unique per size). Rows can be added and removed freely before creation.
- ≥1 size required — enforced by the shared Zod schema (and by the API on `POST /products`).

**Edit modal**: the same product fields, with sizes managed in an expandable "Sizes" section of the same modal:
- Existing sizes: edit label, SKU (global uniqueness enforced — 409 handled as in create) and position, toggle active/inactive (soft — same confirm pattern as product retire/reactivate) → `PATCH /products/:id/sizes/:sizeId`.
- Add new sizes → `POST /products/:id/sizes`.
- **No delete** of existing sizes — deactivation only (referenced sizes are protected regardless).

The image stays per product (one image, not per size).

## States
Defaults from ../shared/components.md apply. Page-specific:
- Products empty state: "No products yet" + "New product"; with filters: "No results" + "Clear filters".
- Retired products stay listed (default status filter: All) with `badge-inactive` "Inactive"; they remain editable.
- Image upload pending: modal shows a per-field uploading indicator; the submit flow stays disabled until it resolves.

## Flows

### Create product (create-then-upload)
1. "New product" → modal. Fill product fields, then build the size rows (preset button prefill or manual rows). Submit → `POST /products { name, categoryId, description?, sizes: [{ label, sku, position }] }` (**no image in this call**; ≥1 size required, Zod + API).
2. On success, if an image was selected: `POST /products/:id/image` (multipart) with the returned id — the product stores the URL (RF-17).
3. Both OK: close, toast "Product created", invalidate products list.
4. Product created but image upload failed: close is still valid — toast error "The product was created, but the image upload failed. Try again from Edit." Invalidate list; never retry `POST /products`.
5. **409 (duplicate SKU)**: inline error on each offending size row — the API names them in `details` (`sizes.N.sku`) with the message to show ("SKU X is already in use" / "SKU X is repeated in this product", architecture.md §7); modal stays open; nothing was created. 400: inline field errors (missing sizes: "Add at least one size").

### Edit product
1. "Edit" → prefilled modal. Submit → `PATCH /products/:id` (changed product fields only); if a new image was chosen → `POST /products/:id/image` after the PATCH succeeds.
2. Success: close, toast "Product updated", invalidate list.
3. Size edits in the "Sizes" section are their own mutations: label/SKU/position change → `PATCH /products/:id/sizes/:sizeId`; new row → `POST /products/:id/sizes`. 409 on a size SKU or label (create or edit): inline error on that row's field — the API names it in `details` (`sku` / `label`) with the message to show (architecture.md §7). Both size routes answer the whole product: replace it in the products cache.

### Deactivate / reactivate size
1. Toggle on an existing size → confirm modal (same pattern as product retire): "Deactivate size “42” of “Nike Air Max”? It can no longer be added to assortments or lists; existing entries and history are unaffected." Confirm is `button-danger`; reactivation uses `button-primary`.
2. Confirm → `PATCH /products/:id/sizes/:sizeId { is_active: false|true }` (soft — sizes are never deleted).
3. Success: toast "Size deactivated" / "Size reactivated", invalidate the products list (size counts) and the open modal's data.

### Retire / reactivate product
1. "Retire" → confirm modal (RN-08 copy states the effect): "Retire the product “Nike Air Max”? It can no longer be added to assortments; existing entries and history are unaffected." Confirm is `button-danger`. Reactivation: "Reactivate…?" with `button-primary`.
2. Confirm → `PATCH /products/:id { is_active: false|true }` (soft, RF-16).
3. Success: toast "Product retired" / "Product reactivated", invalidate products list (and any assortment-picker queries elsewhere).

### Create / edit category
1. Modal submit → `POST /categories { name, description? }` / `PATCH /categories/:id`.
2. Success: close, toast "Category created/updated", invalidate categories list **and** the category filter/select options.
3. 409 (slug conflict, RN-10 — **create only**: the slug is stable on rename, so `PATCH` never answers 409; architecture.md §7): inline error on Name "A category with an equivalent name already exists". A 400 on `name` ("Name must contain letters or numbers") shows inline the same way.

## Edge cases
- Image > 5MB or wrong type: reject client-side before upload (inline error "The image cannot exceed 5 MB"); still handle the API 413/400 with the same inline error.
- Preset buttons ("Clothing", "Footwear", "One size") replace the current size rows in the create modal; if rows already have content, confirm before overwriting. Presets are prefill only — the shared constants never constrain what labels a product may use.
- Category select in the product modal has no "create category" shortcut — switch to the Categories tab (keep MVP simple).
- Switching tabs preserves each tab's own filter params in the URL or resets them — pick one; resetting the other tab's params on switch is the simpler contract. Tab switch never loses in-progress modal state (modals block navigation naturally).
- A retired product referenced by existing assortments/lists renders normally in store views (RN-08); nothing to handle here beyond the confirm copy.
- Editing a product's category is allowed (FK RESTRICT only guards category deletion, which the MVP doesn't expose).

## As built (8.5)
- `pages/PlatformCatalogPage.tsx`, route `/platform/catalog` behind `RouteGuard permission="catalog:manage"` — **not** store-scoped. The nav's Platform section ships "Global catalog" (by permission).
- Tabs: `?tab=categories` opens Categories; an absent or unknown `tab` is Products (the default never appears in the URL, like page 1). The tabs are **links** in `<nav aria-label="Catalog sections">` with `aria-current="page"` on the active one (the URL is the state, so a link — not an ARIA tablist — is the honest element; middle-click/copy work). Each tab link carries only its own `tab` value, so switching drops the other tab's params (the "reset" contract of §Edge cases). Visual per the prototype: 44px text tabs, active = `text` + a 16×2px `accent-bright` rule beneath, hover `surface-raised` + `accent-bright`.
- The header action follows the tab: "New category" on Categories, "New product" on Products (8.6).
- Categories table: `GET /categories?pageSize=100` under `['categories', { pageSize: 100 }]` — the **same** query the store-side category filter and the ProductPicker rail read (one cache entry). Columns Name / Slug / Description (one line, ellipsis, full text in `title`; "—" when null) / Edit row action ("Edit <name>"). Products column omitted (no count in the API). No pagination; empty state "No categories yet" + "New category".
- One form modal for create/edit: Name, Slug (edit only, read-only) and "Description (optional)" (textarea, ≤500). Client validation and the request body both come from the shared `createCategoryBody` (trimmed; a blank description is sent as `null`); edit sends `{ name, description }` as `PATCH`. Inline: 409 on Name; 400 details on `name` / `description`. Anything else is an error toast with the modal open.
- After a write: invalidate the `['categories']` prefix (list + every filter/select source); after an edit also `['products']` (product rows carry `categoryName`).
- `FormField` (label + control + hint/error caption) lifted from `PlatformUsersPage` to `components/FormField.tsx` — now shared by the users and category modals (8.6/8.7 product modals should reuse it).

## As built (8.6)
- The Products tab lives in `pages/PlatformProductsTab.tsx` (`ProductsTab`, `ProductCreateModal`); `PlatformCatalogPage` renders it as the default tab and its header action is "New product".
- Table: Product (32px `ProductThumb` + name), Sizes ("N sizes", every size incl. inactive), Category, Status ("Active" / `badge-inactive`). Filters `search` / `categoryId` / `isActive` + `page` in the URL via `useListParams`; status default **All** (absent param, no `isActive` sent), `true` / `false` explicit. Query key `['products', { page, search, categoryId, isActive: 'all'|'true'|'false' }]` — the same shape as the store-side `/catalog`, so equal filters share one cache entry. Empty: "No products yet" + "New product"; filtered: "No results" + "Clear filters". Row actions (last column): see §As built (8.7).
- Create modal field order: Name, Category (`['categories', { pageSize: 100 }]`, placeholder "Select a category" — also the client error for no choice), Description (optional, ≤2000), Image (optional), Sizes.
- Sizes editor starts with **no rows** (hint "Pick a preset or add sizes one by one."). Preset buttons in `Object.values(SIZE_PRESETS)` order fill labels with empty SKUs; a preset over rows where any label or SKU is non-blank opens a "Replace sizes?" confirm (`button-danger` "Replace sizes"); empty rows are replaced silently. Rows: label + SKU inputs (aria-labels "Size N label" / "Size N SKU") and a remove icon button; "Add size" appends. Position is the row order (sent explicitly as the index); not editable at creation.
- Validation: client and body both from the shared `createProductBody` (so "Add at least one size", per-row "Label is required" / "SKU is required" / repeated label). Adding or removing a row does not re-validate; row errors are keyed by row, so they stay on their row when an earlier row is removed. API 400/409 `details` map by path (`name`, `description`, `categoryId`, `sizes`, `sizes.N.label|sku`); details with no known path → toast.
- Image: `accept` jpeg/png; on pick the file is checked client-side (type `image/jpeg|png`, ≤ 5 MB inclusive) with the API's messages inline; a rejected file blocks submit until replaced. The chosen file name shows as the field hint.
- Create-then-upload: one mutation runs `POST /products` then, with an image, `POST /products/:id/image` (FormData `image`; `apiClient` now sends `FormData` as-is, no JSON content type). While uploading, the submit reads "Uploading image…" and the image hint "Uploading…". Any upload failure (incl. a 413/400 the client checks should have prevented) → error toast "The product was created, but the image upload failed. Try again from Edit.", modal closes, `['products']` invalidated. Success → "Product created" + `['products']` invalidated (platform table, store-side picker and catalog).

## As built (8.7)
- Row actions (last column, `inline-flex` like `/platform/users`): "Edit <name>" on every row and "Retire <name>" (`archive`) / "Reactivate <name>" (`unarchive`) by status. No delete. The edit modal remounts per opening (`Opened<T>` + `seq`), so it always starts from the row's current product.
- Retire / reactivate: `ConfirmModal` with the RN-08 copy (§Flows); reactivation copy "Reactivate the product “X”? It can be added to assortments again." (`button-primary`). Success toast "Product retired" / "Product reactivated"; success **or** failure re-reads `['products']` and closes the confirm (a failure is a toast — e.g. a 404 from another tab).
- Edit modal (`pages/PlatformProductEditModal.tsx`): Name, Category, Description (optional), Image (optional), Sizes — same order and validation source as create (`updateProductBody` on all three fields, then **only the fields that differ** from the latest saved product are sent; a cleared description is `null`). Nothing changed and no image → closes without a request. "Save changes" runs `PATCH` (if any field changed) then, with a new image, `POST /products/:id/image`; pending label "Saving…" / "Uploading image…".
- The modal keeps the latest `Product` any write answered (PATCH, size routes, upload) and diffs against it; every successful write also invalidates the `['products']` family (platform table, store-side picker/catalog). So after "fields saved, upload failed", a retry only re-uploads.
- Image replacement: same client checks as create (shared `ImageField` / `imageProblem` in `pages/platformProductCommon.tsx`, with `PRODUCTS`, `CATEGORY_OPTIONS`, `IMAGE_TYPES`, `IMAGE_MAX_BYTES`, `uploadProductImage`). Hint "JPEG or PNG, up to 5 MB — replaces the current image" when one exists. An upload 400/413 with an `image` detail is inline under Image and the modal stays open; any other upload failure is a toast with the modal open (unlike create, there is no partial product to explain).
- **Sizes section — saved per row, not on "Save changes"** (§Flows · Edit product step 3: size edits are their own mutations). A disclosure button "Sizes (N)" (`aria-expanded`, collapsed by default) reveals an ordered list of every size, inactive ones with `badge-inactive`. Each row: label, SKU, position (number 0–9999) inputs + "Save" (enabled only when the row differs from its saved values; sends only the changed fields) + "Deactivate" / "Reactivate". Enter in a row field saves that row and never submits the product form. Client checks: label/SKU via `updateProductSizeBody`, position "Enter a whole number from 0 to 9999". Rows are keyed by their saved values, so a saved row restarts from the server's answer while other rows keep their unsaved drafts.
- "Add size" opens one new row (label + SKU, "Save" / discard icon) → `POST /products/:id/sizes` without a position (the API appends after the last size); "Size added", the row closes and the new size is listed from the answer.
- Size 400/409 `details` (`label` / `sku` / `position`) render inline on that row only; any 404 in the modal (product or size gone in another tab) → error toast, modal closes, `['products']` re-read; anything else → toast with the modal open.
- Size activation: confirm per §Flows · Deactivate / reactivate size; reactivation copy "Reactivate size “42” of “X”? It can be added to assortments and lists again." Toasts "Size deactivated" / "Size reactivated"; the row then shows/drops the Inactive badge.
- Two-tab conflicts: last write wins (no version checks in the API); each write answers the whole product, so the modal shows the server's state after any write, including changes made elsewhere.
