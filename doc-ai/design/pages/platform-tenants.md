# Stores — `/platform/tenants`

> Guard: `tenant:manage` · Zone: platform
> API: `GET /tenants`, `POST /tenants`, `PATCH /tenants/:id`

## Purpose
Platform Admin management of stores (tenants): list, create, rename, and activate/deactivate (RF-06..08). Platform-zone page: no tenant context, no `X-Tenant-Id` header on any call (architecture.md §5.2 — the tenants router never mounts `tenantContext`).

## Layout
Standard list screen skeleton (../shared/layout.md shell + DESIGN.md §Screen Skeletons): `<PageHeader>` with title "Stores", subtitle "N stores on the platform" from the tenants envelope's `total` (platform zone — no store name, `../shared/components.md` §`<PageHeader>`), and primary action "New store" → filter band → `<DataTable>` → `<Pagination>`.

## Content

### Table
| Column | Source | Notes |
|---|---|---|
| Name | `name` | body-medium |
| Slug | `slug` | muted caption |
| Status | `is_active` | "Active" (plain text) / `badge-inactive` "Inactive" |
| Created | `created_at` | date convention from ../shared/components.md |
| Users | user count | **Nice-to-have**: render only if the API response includes a count (`GET /tenants` may add it cheaply); omit the column otherwise. Never issue N extra requests for it. |

Row actions (icon-button-ivory): "Edit" (opens edit modal). No delete action exists (RN-08).

### Filter band
- Search input (placeholder "Search stores…"), debounced, state in URL (per ../shared/components.md).
- Pagination driven by `{ items, page, pageSize, total }`.

### Create modal — "New store"
Form modal (max-w 640px). Single field: **Name** (required). The slug is NOT an input: it is generated by the API from the name (RN-10). After successful creation the modal may show the resulting slug read-only before closing, or simply close — the slug is always visible in the table.

### Edit modal — "Edit store"
Fields: **Name** (editable) + **Slug** (read-only, muted). Separate from the name form, an activation control: toggle/button "Deactivate store" / "Reactivate store".

## Actions by permission
| Action | Permission | Behavior |
|---|---|---|
| View list | `tenant:manage` | Route guard; page is invisible below this permission |
| New store | `tenant:manage` | Opens create modal → `POST /tenants` |
| Edit name | `tenant:manage` | Edit modal → `PATCH /tenants/:id` |
| Deactivate / Reactivate | `tenant:manage` | Confirm modal → `PATCH /tenants/:id` with `is_active` |
| Delete | — | **Does not exist** (RN-08: stores are never deleted) |

## States
Defaults from ../shared/components.md apply. Page-specific:
- Empty state (no tenants at all): "No stores yet" + "New store" action.
- Empty search results: "No results for this search" + "Clear filters".
- Inactive rows are fully visible and editable (deactivation is reversible), marked only by the badge.

## Flows

### Create store
1. "New store" → modal with Name.
2. Submit → `POST /tenants { name }`.
3. Success: close modal, toast "Store created", invalidate the tenants list query. New store appears with its API-generated slug.
4. **409 (slug conflict)**: the generated slug already exists → inline error on the Name field: "A store with an equivalent name already exists"; modal stays open.
5. 400: inline field errors per ../shared/components.md.

### Edit name
1. Row action → edit modal prefilled.
2. Submit → `PATCH /tenants/:id { name }`. Success: close + toast "Store updated" + invalidate list. 409 on slug conflict → same inline error as create (if the API regenerates the slug on rename; otherwise N/A).

### Deactivate / reactivate
1. Toggle in edit modal (or row action) → **confirm modal** (max-w 480px). Deactivation copy must state the consequence (RF-05): "Deactivate the store “Downtown Store”? Its users will not be able to operate while it is deactivated." Confirm button is `button-danger` for deactivation, `button-primary` for reactivation ("Reactivate the store “…”?").
2. Confirm → `PATCH /tenants/:id { is_active: false|true }`.
3. Success: toast "Store deactivated" / "Store reactivated", invalidate list. Error: error toast, state unchanged.

## Edge cases
- **No delete anywhere** — not in the row, not in the modal (RN-08). If a future API 405/403 is ever received for an attempted delete, it is a bug in the UI, not a state to design for.
- Deactivating a store does not log out its users immediately; they get 401 on their next request (RF-05, profile check per request). No UI handling needed here beyond the confirm copy.
- The Platform Admin's tenant selector (sidebar) lists **active** stores only; after deactivating the currently selected store, the selector must drop it and clear the selection (invalidate the selector's source query on any `is_active` change).
- Search matching an inactive store still returns it — deactivated stores must remain findable and reactivable.
- Concurrent rename causing 409: identical handling to create.
